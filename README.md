# ATAM Automation Pipeline

**🌟 Live Demo:** A deployed version of the evaluation dashboard is available at [https://atam-automation.vercel.app/introduction](https://atam-automation.vercel.app/introduction)

This repository contains the prototype for a fully automated, LLM-assisted Architecture Tradeoff Analysis Method (ATAM) pipeline. 

## 🎯 Aim of the Project
The primary objective of this project is to automate the most labor-intensive phases of the conventional ATAM process. By decoupling qualitative generative AI reasoning from deterministic mathematical aggregation, this pipeline acts as an analytical assistant for software architects. 

It takes structured architectural descriptions and business scenarios as inputs, forces a Large Language Model (LLM) to extract component-level catalysts and obstacles, and then uses a Python backend to algorithmically compute Component Sensitivities and detect cross-scenario Trade-offs between Quality Attributes.

## ⚙️ Requirements & Installation

This project consists of a Python backend and a TypeScript/Next.js frontend. 

### Python Backend
*   **Python 3.10+**
*   **Dependencies:** Install the required Python packages using `pip`:
    ```bash
    pip install -r requirements.txt
    ```
*   **Environment Variables:** Copy the `.env.example` to `.env` (if applicable) and add your OpenRouter API key if you are using cloud LLMs.

### Next.js Frontend
*   **Node.js 18+**
*   Navigate to the frontend directory and install the packages:
    ```bash
    cd frontend
    npm install
    ```

## 🚀 How to Run the Pipeline

The system is executed in two distinct phases: running the backend analysis to generate the data, and then running the frontend to visualize it.

### 1. Running the Python Backend
The pipeline is executed via a Jupyter Notebook, which makes it easy to step through the data loading and evaluation phases.
1. Open `atam/atam_base.ipynb` in PyCharm (or Jupyter).
2. Execute the cell. The notebook will invoke `run_base_pipeline()`.
3. The LLM will process the `scenarios.json` and `architectures.json` files.
4. The output metrics (sensitivities, trade-offs, and architecture summaries) will be written to the `outputs/` directory in a timestamped run folder.

### 2. Changing the Target Domain (MiSArch vs SecuRooms)
If you want to evaluate a different architecture domain, you must update both the Backend (to generate the data) and the Frontend (to visualize the correct run).

**Step A: Generate the Data (Backend)**
1. Ensure your domain data (e.g., `misarch` or `secure-rooms-system`) is placed inside the `data/` directory. It must contain a `scenarios.json` file and an `architectures/` folder.
2. Open `atam/atam_base.ipynb` and execute the notebook. 
3. The notebook automatically discovers *all* valid domain folders in the `data/` directory and runs the pipeline for each of them. The new results will be generated in timestamped folders under `outputs/<domain_name>/`.

**Step B: Point the Frontend to the New Data**
Because the frontend is decoupled from the backend, you must explicitly tell it which run to load.
1. Open the file `frontend/lib/data.ts`.
2. Modify the `DOMAIN` and `RUN` constants at the top of the file to match the exact folder names generated by your backend:
    ```typescript
    const DOMAIN = "online-learning-platform" // or "secure-rooms-system"
    const RUN = "run-YYYYMMDD-HHMMSS" // The exact timestamped folder name inside outputs/<domain>/
    ```

### 3. Running the Next.js Frontend
Once the backend has successfully generated the JSON artifacts in the `outputs/` directory, you can spin up the web dashboard to visualize the trade-offs.
1. Open a terminal and navigate to the frontend:
    ```bash
    cd frontend
    ```
2. Start the development server:
    ```bash
    npm run dev
    ```
3. Open your browser and navigate to `http://localhost:3000`. The frontend will automatically parse the generated JSON artifacts from the file system and render the interactive evaluation dashboard.
